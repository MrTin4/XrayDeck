## 1. 背景与目标

1. xray-core 已在 Windows 上安装，并通过 WinSW 以 Windows 服务的形式运行，目前缺少管理面板。
2. xray-core 已开启 API，但实际服务列表及方法支持情况需要在连接后检测，不能假定所有 API 均可用。
3. XrayDeck 用于查看节点和运行状态，以及检查和升级 xray-core。代理分组与手动节点切换仅在 API 完整支持时提供，不支持时放弃此功能。

## 2. 首版范围与技术要求

1. 首版支持 Windows 10/11 x64，使用 Rust 开发，以便携版发布；ARM64 后续增加。
2. 界面库使用 [longbridge/gpui-kit](https://github.com/longbridge/gpui-kit)。
3. 正常使用无需管理员权限。涉及 Windows 服务操作时，按需弹出 UAC，由独立的提权辅助进程执行；主界面保持普通用户权限。
4. 升级如需写入受保护的安装目录，同样由提权辅助进程完成。用户拒绝 UAC 时停止相关操作并保留现状。
5. 关闭窗口即退出程序，不进入托盘。退出 XrayDeck 不停止 xray-core 服务。
6. 本地存储默认位于 `%APPDATA%\XrayDeck\`，用于应用设置、日志、更新缓存及升级备份；敏感节点凭据不写入日志。
7. 升级进入停止服务、替换文件、启动或回滚阶段后，关闭窗口应等待本次关键操作完成再退出，避免遗留停服或文件替换未完成的状态。

## 3. 功能需求

### 3.1 连接配置与 API 服务发现

1. 允许设置 XrayDeck 连接的 xray-core gRPC API 地址，并保存到本地应用设置。
2. 此设置仅决定本工具连接哪个地址，不修改 xray-core 的 `api` 配置。
3. 提供连接测试，显示已连接、连接中、无法连接及具体错误。
4. 通过 gRPC Server Reflection 获取服务端实际公开的 API 服务列表，并展示服务名称。
5. 完整发现依赖 xray-core 开启 `ReflectionService`。未开启时显示“无法完整发现 API 服务”，不能把无法发现解释为没有开启其他服务。
6. Reflection 不可用时，可通过已有的只读方法探测所需能力；结果区分可用、不支持、无法确定。禁止为了探测能力调用写入接口。
7. 按实际支持的方法启用功能。服务已注册不等于其依赖模块已经配置或调用一定成功；不同兼容命名空间的服务别名可合并展示。
8. 本机联调 API 地址为 `127.0.0.1:8080`，作为首次连接的预填值，允许用户修改。

### 3.2 节点数据

1. 通过 `HandlerService.ListOutbounds` 获取运行时出站数据，不以读取本地配置文件替代此需求。
2. 使用 outbound tag 标识节点，展示 API 可提供的名称/tag、协议、服务器地址和端口等信息；缺失字段明确显示未知。
3. 直连、阻断、DNS 等非代理出站应与可用代理节点区分展示。
4. 不支持的协议仍可显示 tag 及可识别信息，不应导致整个列表加载失败。
5. 目标版本没有 `ListOutbounds`，或未开启 `HandlerService` 时，提示相应限制，不展示虚构节点数据。
6. 出站列表默认按观测延迟从小到大排列，不可达、缺失或负延迟的记录置于末尾，相同延迟保持原顺序。移除独立排序按钮，点击“观测延迟”表头在延迟升序、降序间切换，点击“观测时间”表头在时间升序、降序间切换；跨列切换从升序开始，当前列显示 ↑/↓，非当前可排序列显示 ↕。排序对代理及系统出站均生效，纯本地操作，后台读取期间也可切换。
7. 未返回观测记录的时间显示“—”；已有观测但时间为零、负值或无法转换时显示“核心未提供”。所有无效/缺失时间在升序和降序中均置于末尾；同一时间或均无有效时间的节点保持原相对顺序。时间按时间戳比较，以本地时间显示，不以客户端读取时间补造。
8. 排序只调整本地展示，不调用网络、不触发测速、不修改核心；刷新出站和切换页面保留当前排序，本次应用会话结束后恢复默认排序。
9. 延迟排序使用核心已有观测延迟，按毫秒数升序/降序排列（0 ms 有效）；两种方向下不可达、缺失或负延迟均置后，相同延迟或均无有效延迟时保持原相对顺序。负延迟显示“暂无数据”。

### 3.3 代理分组及当前出站

1. 分组信息仅通过 API 获取，不读取本地 Xray 配置补齐，不要求用户登记分组元数据。
2. API 能完整提供分组、成员、类型及当前选择时，列举分组并展示实际状态；API 不能提供时放弃该功能，不作为开发阻塞项。
3. 手动分组定义为“不通过负载均衡器选择节点的分组”。`routing.balancers` 不属于手动分组，即使可设置覆盖目标也不改变其分类。
4. 当前核对的 Xray 公开接口缺少完整分组枚举及非负载均衡手动分组模型。因此首版按不提供分组列表和手动切换设计，除非目标实例的 API 验证证明具备相应能力。
5. `GetBalancerInfo` 需要已知 balancer tag，其返回值不能替代完整分组发现；不将 `principle_target` 一概解释为完整成员或某次连接实际使用的节点。
6. 节点列表仍通过 API 独立提供。缺少分组状态时，不推测全局唯一“当前节点”，也不把任意出站标为已选中。

### 3.4 手动分组切换与持久化

1. 仅当 API 能识别符合 3.3 定义的手动分组，并提供对应选择接口时，开放出站切换；否则放弃切换功能。
2. 不以 `RoutingService.OverrideBalancerTarget` 覆盖负载均衡结果来替代手动分组切换，不为实现切换而修改路由或重写本地配置。
3. 候选成员、当前选择及切换结果必须通过 API 获取和确认；成员关系或类型未知时不开放操作。
4. 负载均衡器不提供手动切换入口。
5. 切换作用于该分组后续的路由选择，不承诺迁移已有连接。
6. 如果目标 xray-core 提供原生持久化能力，则依托该能力保存选择；否则不实现选择持久化，不写回 Xray 配置，也不在重启后自动恢复覆盖目标。
7. 本次核对未发现相关公开接口提供跨重启保存选择的能力，现有覆盖逻辑属于运行时状态。因此，首版按不持久化切换结果设计；这不影响 XrayDeck 自身连接设置的本地保存。

### 3.5 HTTPS 延迟测速及接口限制

#### 3.5.1 期望功能

1. 如果 xray-core API 提供按需测速能力，则支持对单个节点或全部代理节点进行 HTTPS 延迟测速。
2. 不需要支持取消测速，不包含下载带宽测速。
3. 结果显示节点 tag、延迟（毫秒）、可达状态、测试时间及错误信息，测试期间界面保持响应。
4. HTTPS 请求必须经过被测出站，不能用 API 响应耗时、TCP 连接耗时或路由模拟结果冒充 HTTPS 延迟。

#### 3.5.2 已确认的上游能力

1. Xray 的 Observatory 模块能够在核心内部通过指定出站执行周期性 HTTP/HTTPS 探测。探测 URL、节点选择范围和间隔由核心配置决定。
2. 公开的 `ObservatoryService.GetOutboundStatus` 仅返回已有观测结果，包括 outbound tag、延迟、可达状态和最近探测时间；该请求不接收节点 tag 或测试 URL，也不触发立即测速。
3. `RoutingService.TestRoute` 只计算路由结果，不执行网络延迟测速。
4. 因此，目前不能仅凭公开 API 实现“点击后立即对单个/全部节点发起 HTTPS 测速”。依照上述条件要求，首版不承诺该主动测速功能。v2rayN 的临时核心方案可作为扩展实现参考，见第 8 节，尚未纳入首版范围。
5. 可以增加已有观测结果展示：服务和观测模块可用时读取数据，允许查看单节点或全部返回结果，明确标记为“核心最近观测结果”。刷新按钮只重新读取结果，不标记为重新测速。
6. 只有确认核心观测 URL 使用 HTTPS 时，才将结果标为 HTTPS 延迟；现有观测 API 不返回 URL，无法确认时统一显示为“核心观测延迟”。未被观测的节点显示“暂无数据”。
7. 如果后续目标版本新增按需测速 API，再按 3.5.1 开放单节点及全部节点测速，并补充测试参数与验收标准。
8. 区分普通 Observatory 与 Burst 观测数据，读取 `OutboundStatus.health_ping`（字段 7）的存在性识别 Burst；`last_try_time` 仍按官方字段 6 解码。Xray 26.10.10 的 [Burst 实现](https://github.com/XTLS/Xray-core/blob/v26.10.10/app/observatory/burst/burstobserver.go)将探测与最近存活时间固定设为 0，不能仅通过当前 API 恢复真实探测时间。界面显示“核心未提供”并解释来源限制；普通 Observatory 返回有效 Unix 秒时间时正常显示、排序。不自动切换核心模块或重启服务。

### 3.6 当前版本与更新检测

1. 界面仅显示当前运行的 xray-core 版本，不再额外显示核心文件版本；内部保留文件版本数据用于更新比较与升级校验。
2. 本次核对的标准 API 未提供专门的运行版本查询方法，不能通过节点 API 或系统统计接口直接获取版本。
3. 对本地 WinSW 托管实例，通过服务/API 进程与核心路径关联定位核心文件，执行 `--version` 获取版本，不再读取启动日志。此命令直接证明所执行文件的版本，不代表读取了运行进程内存中的版本，界面需保留查询来源说明。
4. 运行版本读取中显示“读取中”，无法识别时显示未知，设置页保留查询来源与失败原因；不另行展示文件版本字段。首次使用时由用户指定 Windows 服务名、WinSW 配置和 xray.exe 路径，程序自动校验关联关系，用于版本识别和升级。
5. 通过 Project X 官方发布渠道检查更新：以官方 `XTLS/Xray-core` GitHub Releases 及其发布 API 为机器可读来源，不依赖解析网站页面布局。
6. 展示当前版本、可用版本、发布日期、发布说明链接、检查时间及检查失败原因；区分正式版和预发布版。版本比较使用结构化版本信息，不能直接按字符串排序。
7. 默认只提示正式版更新，可在设置中启用包含预发布版；用户主动发起升级，不静默安装。检测失败不影响节点管理。
8. 参考 v2rayN，通过本地核心命令获取文件版本、通过官方 Releases 查询可用版本；这两项不是对运行实例的 gRPC 版本查询。命令参数应按实际目标版本验证，不直接依赖其他客户端的固定参数。
9. 应用启动读取已保存设置后，以及保存核心路径或服务关联配置后，后台查询版本并校验服务关联；界面仅展示运行版本。服务名、WinSW 配置或 API 未配置正确时，关联失败原因在设置页展示；查询来源与路径说明保留。
10. 重新启动时重新查询并校验，不将上次保存路径等同于已验证关联。内部更新比较可以使用已读取的文件版本，升级仍须通过完整服务关联校验；移除文件版本展示不改变比较、校验及升级流程。
11. 本地 WinSW 实例在 API 进程与服务归属校验通过后，执行关联核心路径的 `--version` 命令获取版本；可查询进程映像路径时，必须先确认它与配置核心路径一致。不要求日志存在或具有某种格式，彻底移除启动日志读取、解析与时间匹配逻辑。
12. 受权限限制无法直接查询实际映像路径时，允许使用已通过 Windows 服务、API 进程归属和 WinSW XML 核验的配置关联路径查询版本；来源必须注明“WinSW 服务配置关联路径”，并说明并非内存映像版本。命令执行失败、不返回有效 Xray 版本或超过 5 秒时显示诊断，不读取日志回退；退出成功且版本横幅正确才接受结果。
13. 顶部与设置页从关联核心命令结果显示版本，设置页附带路径、PID、`--version` 参数与路径验证来源。该查询为普通用户只读操作，不增加 UAC，不停止服务；升级提权后的实际映像路径强制复核要求保持不变。

### 3.7 xray-core 直接升级

1. 用户可从更新提示直接发起本地 xray-core 升级。操作前展示当前版本、目标版本，并提示需要重启服务、现有连接会中断。
2. 升级需要准确关联 API 实例、Windows 服务名、WinSW 配置、实际 xray.exe 路径和核心运行架构。关联不明确时禁止替换文件。
3. API 地址本身不足以定位本地服务；远程 API 地址不支持通过本机文件替换完成升级。
4. 在普通用户权限下下载适合目标核心架构的官方发布包及校验信息，校验完整性后再进入服务操作阶段。无法校验时不执行替换。
   下载直接使用系统网络行为，不提供直连/代理切换或独立代理配置，也不主动读取节点或切换出站以完成下载。
5. 通过 UAC 提权辅助进程完成必要操作：停止目标服务并等待 Xray 进程退出、备份旧核心、替换核心、启动服务并检查运行状态及 API 恢复情况。
6. 仅升级 xray-core，保留现有配置、WinSW 和地理数据等其他文件；不整包覆盖安装目录。
7. 若新版本启动或健康检查失败，尝试恢复旧核心并重新启动，显示升级及回滚结果。即使回滚失败也保留备份和诊断信息，便于恢复。
8. 同一实例同一时间只允许一次升级；显示下载、校验、停服、替换、启动、成功或失败状态。
9. 升级导致 Xray 重启后重新发现 API 能力并刷新节点、分组及版本；不恢复未经核心原生持久化的手动选择。

### 3.8 主页面与独立设置页面

标题区左侧依次显示应用名称、内核版本、更新检查状态及检查更新链接；工具自身版本显示在右侧设置/返回按钮旁。不展示独立核心文件版本及“已有核心的 Windows 管理面板”说明副标题。

1. 应用默认打开主页面，业务内容仅保留版本号、是否有更新及出站列表；允许对应的检查更新、刷新出站和排序操作。标题区整合版本及更新摘要，右侧提供设置入口，不再提供独立通用状态栏。出站状态直接显示在出站板块内。
2. 独立设置页面集中提供 API 地址保存与连接测试、API 服务发现及诊断、本地 Windows 服务关联、WinSW XML 与核心路径、保存及关联校验、更新渠道选择和升级确认。设置文件路径只在设置页展示。
3. 主页面显示应用版本和内核版本；无法确认内核版本时显示未知，移除重复的核心文件版本。未检查时仅保留检查入口；检查结果简化为“可更新至 v…”“已是最新”或“已高于发布版”，不重复展示相同版本号。版本无法比较及检查失败时明确提示，不误报最新；发布版本、渠道及发布时间保留于设置页。
4. 主页面刷新只使用已保存的 API 地址，不隐式保存设置页草稿，不清空已校验的服务关联或更新结果。设置保存时，仅在配置确实变化后使相关旧状态失效，API 地址变化后清空旧实例节点。
5. 页面切换保留输入草稿、节点、排序、服务关联、更新结果和后台任务状态；切换页面本身不保存、不发起网络请求。后台任务期间仍可导航，配置写入和重复后台操作保持禁用。
6. 后续新增需求、交互调整、边界条件、优化与验证结果应在同次实现中同步记录本 PRD，明确区分已验证内容和待验收事项。
7. 版本与更新在主页面显示运行版本、更新摘要与检查链接；渠道、发布日期等完整发布信息保留于设置页。减少页面边距和节点行留白，表头与行列使用一致宽度，服务器文本过长时截断。出站列表使用剩余窗口高度并独立滚动，不再固定最大高度。
8. 出站表头所有标题在对应列内水平居中，表头与数据行共用同一列布局实现，统一左右内边距、列间距、固定列宽及禁止收缩规则；服务器列固定为 230 像素，“节点名称”列自适应占剩余宽度，两列过长文本均可截断。协议、延迟及时间数据居中，名称与服务器数据左对齐。表头和滚动列表预留同样的右侧空间，避免滚动区与表头宽度不一致。表头保持固定，数据行不因纵向空间不足而压缩高度。
9. 移除显示“已连接 · N 个出站”等信息的独立状态控件及其间距；出站标题区域依次显示板块名称、连接/启动/刷新状态与数量及最近读取时间、自动刷新倒计时。长内容允许换行，刷新按钮位于右侧；不再保留重复的列表底部状态行。
10. 检查更新的进行中、比较结果、失败原因及升级进度归入主页面版本信息区，设置页的核心更新区同步显示。出站刷新与更新操作使用独立状态，后续自动刷新不得覆盖上次更新结果或错误，检查更新不得覆盖出站连接信息。保存反馈及本地关联诊断留在设置页内，设置加载失败也必须可见。
11. 移除底部版本栏，将运行版本及更新摘要/进度依次放在应用标题后方；工具版本位于右侧设置按钮旁。标题区可随长状态换行，右侧导航保持可见；出站板块占据标题下的剩余高度并独立滚动，设置页保留完整更新与升级配置。
12. 两个排序表头按钮使用与普通表头相同的文字色 `#94a3b8` 和默认背景色 `#1e293b`，共用颜色常量，避免组件主题色覆盖父级表头色。悬停背景为 `#29384f`，按下背景为 `#334155`；文字及排序箭头保持统一颜色，键盘聚焦提示保留。
13. 普通操作按钮通过统一构造函数创建，文字 `#94a3b8`、默认背景 `#1e293b`、悬停背景 `#29384f`、按下背景 `#334155`。覆盖导航、手动刷新、API 连接测试、自动刷新开关、设置保存、关联校验、渠道选择、升级及确认/返回操作；移除局部 Primary 主题覆盖。各按钮保留自身尺寸、标签、工具提示、事件及禁用条件；禁用状态统一弱化并屏蔽交互，保留键盘聚焦提示。后续新增普通按钮沿用同一构造函数。
14. 检查更新为普通按钮规范的明确例外：标题区和设置页均使用无填充、带下划线的超链接样式，默认文字 `#93c5fd`、悬停文字 `#f8fafc`、按下文字 `#e0f2fe`、禁用文字 `#64748b`。通过组件主题的 link/link_hover/link_active 统一设置正常及交互颜色，避免组件内部状态样式回落到深色文字。保留原有检查动作和忙碌禁用行为，不跳转外部网页，不直接执行升级。
15. 设置页所有输入框通过共用构造函数使用深色底色 `#101827`、禁用底色 `#172033`、边框 `#29354a`，覆盖 API 地址、刷新间隔、Windows 服务名、WinSW XML 与 xray.exe 路径。组件主题切换为深色基准，输入文字及光标 `#e2e8f0`、占位文字 `#94a3b8`、选择背景 `#334155`、聚焦提示 `#93c5fd`，避免浅色主题组件在深色页面显示白底。原有编辑、保存及禁用行为保持不变。
16. “观测结果”说明及能力限制提示置于出站板块内、节点滚动容器之外，固定在列表底部，并用细分隔线区分。仅节点区域滚动，提示不覆盖末尾节点；未提供观测说明时不保留空白提示区。
17. 输入框普通及聚焦状态均使用 1 像素边框，聚焦时只改变边框颜色为 `#93c5fd`，关闭组件主题额外绘制的外部焦点环，避免双层粗框；键盘聚焦仍保留细线可见提示。标题、运行版本、更新状态及检查更新链接按实际文本排版的 ascent、descent 与行高计算 baseline 对齐，不依赖未传递文字基线的 `items_baseline()`；标题与运行版本作为整体参与换行。右侧工具版本与设置/返回按钮按垂直居中对齐。

### 3.9 出站列表自动刷新

1. 在独立设置页提供自动刷新开关和整数秒间隔输入，默认关闭、默认 30 秒；允许 5–86400 秒。保存后生效，开关和间隔持久化至本地设置，旧版设置缺少这些字段时使用默认值。
2. 设置页启用或修改间隔后从新的间隔开始计时，不立即发起请求；应用启动恢复已保存配置，若已开启自动刷新，启动就绪后立即刷新一次出站与已有观测结果，并从首次请求重新开始间隔计时。不触发核心测速、不修改 Xray 配置或路由。
3. 全局只运行一个自动刷新定时循环，使用异步等待保持界面响应。主页面、设置页切换不会创建额外循环；退出应用后终止。计时以单调时钟为准，检查粒度约 1 秒，不受系统时钟调整影响。
4. 设置页、已有后台操作、核心版本与关联读取、升级确认或关闭等待期间，跳过到期刷新，不排队、不补发遗漏周期。返回主页面后按后续周期继续，避免长时间挂起后集中请求。
5. 自动刷新沿用已保存的 API 地址与现有只读读取流程，不保存输入草稿，不清空已校验的服务关联和更新结果；当前排序保持不变。手动刷新后重新计算下一次自动刷新时间，避免相邻重复请求。
6. 刷新期间保留当前节点列表；整体读取失败时显示错误，保留上次成功结果及读取时间，并在后续周期重试，不无限立即重试。主页面显示自动刷新开关状态、已保存间隔和最近成功读取时间。
7. 非整数、空值或超出范围的间隔阻止保存，明确提示范围，不覆盖原有设置及正在使用的计时安排。保存关闭状态后立即停止后续自动请求，已经进行的只读请求允许完成。
8. 出站列表标题旁显示“下次自动刷新：N 秒”，每秒更新，使用调度器真实截止时间计算并向上取整，不维护独立递减计数。到期显示“即将自动刷新…”，不得出现负值或提前显示 0 秒。固定提示区最小宽度，减少倒计时数字变化引起的横向抖动。
9. 实际读取节点时显示“正在刷新出站…”，其他后台任务或升级确认阻止自动刷新时显示暂停及原因，关闭时明确显示已关闭；手动刷新、保存间隔变更、跳过周期与关闭功能时，倒计时同步实际调度。恢复主页面后显示当前计划的真实剩余时间，长时间挂起不补发周期。倒计时描述的是客户端读取已有结果的时间，不是核心测速时间。
10. 启动读取设置成功后，出站板块内明确显示启动忙碌，核心版本与服务关联检查期间禁用会与启动冲突的操作。检查结束后转为就绪，已开启自动刷新时立即发起一次读取；一次启动只触发一次，后续保存或重试本地校验不重复触发。启动定时器在等待检查时不发起刷新，首次请求重置后续倒计时，避免短时间内重复请求。
11. 未配置核心路径时无需等待本地检查，直接就绪；核心文件版本读取或服务关联校验失败保留独立诊断，仍允许启动首次 API 刷新。设置加载失败时保留错误且不自动刷新；未开启自动刷新时启动就绪不自动读取节点。首次请求失败后按原间隔重试，不形成立即重试循环。

## 4. 异常与状态处理

1. API 不可达、方法不支持、Reflection 未开启、模块未配置、文件无权限、UAC 被拒绝、下载失败和升级失败均需要明确提示。
2. 不将“检测失败”展示为“没有服务”“没有分组”或“已经是最新版”。
3. 切换调用超时或连接中断时重新读取真实状态；无法确认则显示状态未知。
4. Xray 重启或更新后重新建立连接，不沿用过期的 API 能力和当前节点状态。

## 5. 首版验收标准

1. 普通用户可启动程序、保存 API 地址、连接核心、读取节点及可用的只读状态，无需 UAC。
2. 开启 Reflection 时可列举实际 API 服务；未开启时明确说明限制，并区分已经验证与尚未确认的能力。
3. 支持节点读取的方法可用时正确展示运行时数据，不支持时显示具体原因。
4. 分组仅通过 API 获取；API 不支持时不展示分组和切换操作，不要求本地配置或手动登记补齐。不得将负载均衡器覆盖操作视为手动分组切换。
5. 观测结果保留实际时间与状态，不将读取缓存结果宣称为发起测速；无按需 API 时不提供虚假的主动测速按钮。
6. 应用设置默认保存在 `%APPDATA%\XrayDeck\`；Xray 选择无原生持久化能力时不恢复。
7. 更新检测能提示可用版本和检查错误；用户发起升级时按需 UAC，成功后验证新核心，失败后尝试回滚。
8. 运行版本无法确认时明确展示未知及查询来源或失败原因，不重复显示文件版本；关闭窗口退出应用，不进入托盘，不停止核心服务。
9. 首次使用指定服务名、WinSW 配置及核心路径，关联校验不通过时禁止升级；便携版在 Windows 10/11 x64 上验收。
10. 默认只提示正式版，可开启预发布版；下载使用系统网络，不出现独立代理配置选项。
11. 主页面仅呈现版本、更新状态与出站列表；所有配置及诊断、升级入口位于独立设置页，支持往返导航且保留会话状态。
12. 点击观测时间表头可切换最新/最早优先；相同时间保持稳定顺序，无效和缺失时间在两种排序下均排末尾，观测不可达但时间有效的节点正常参与排序。
13. 点击延迟表头切换升序和降序，按可达节点的非负毫秒数排列，0 ms 有效，同值稳定；两种方向下不可达、缺失或负延迟均置后。无观测或空列表可正常展示，独立排序按钮已移除，表头保持居中且与数据列对齐。
14. 已保存有效核心路径和服务关联配置时，应用启动后自动查询运行版本；关联失败时显示失败原因。服务名与 XML ID 不一致时提示正确 ID，避免误填 WinSW 可执行文件名。重新打开应用仍会自动校验，不依赖上次会话的关联状态；不另行显示文件版本字段。
15. 出站表头五个标题分别在所属列内居中；表头和列表项的列边界一致，长文本不会挤压相邻固定列，滚动时表头位置固定，列表项保持正常行高。
16. 自动刷新启用、间隔变更、关闭和重启恢复行为正确；旧版配置兼容，非法间隔不能覆盖有效配置。忙碌时跳过不积压，手动刷新推迟下一次自动刷新，设置页暂停自动读取；刷新期间及整体失败时保留已有列表，排序保持不变。
17. 倒计时与实际调度一致，每秒更新，截止前不足一秒仍显示 1 秒，到期不出现负数；手动刷新、间隔修改、跳过周期和关闭功能均同步状态。节点刷新与其他后台操作的提示可区分。
18. 启动检查期间显示忙碌；开启自动刷新时，检查结束立即读取一次并重置倒计时，后续本地校验不重复触发。无核心路径或本地检查失败时仍可首次读取；自动刷新关闭或设置加载失败时不发起首次自动请求。
19. 主页面不存在独立通用状态栏；出站连接信息在出站区显示，更新检查及升级状态在版本区显示。自动刷新后更新结果/错误仍保留，检查更新后出站数量和最近读取时间仍可见。设置保存与本地校验诊断可在设置页查看。
20. 出站连接信息显示在自动刷新倒计时前方，列表下方无重复状态行；核心版本及更新信息跟随应用标题，工具版本紧邻设置按钮，不再保留底部版本栏，出站列表使用剩余空间。
21. 光标未悬停时，两个排序表头按钮的文字、箭头及背景与其他表头保持一致；悬停、按下时仅使用统一的背景层次提示可点击，排序行为与居中布局保持不变。
22. 主页面与设置页的普通操作按钮均采用统一配色规范；检查更新使用明确规定的超链接样式，其禁用与检查行为不变，支持键盘聚焦和触发。
23. 设置页五类输入框均无突兀白底，正常及禁用状态保持深色；输入、占位、选区与光标可辨识，聚焦提示清晰，原有内容与保存行为不受影响。
24. 检查更新链接悬停后文字保持明亮可读，按下与禁用状态颜色明确；主页面和设置页表现一致。“观测结果”提示在滚动至任意节点时均保持位于列表底部，不随内容滚动或覆盖节点。
25. 设置页输入框聚焦时只有细高亮边框，不出现粗外圈或因边框变宽导致布局跳动；标题与版本及检查更新链接按 baseline 对齐，工具版本与设置按钮居中，主页面和设置页保持一致。
26. 核心版本来自关联文件的 `--version` 命令，未读取任何启动日志；来源明确说明路径验证情况。版本输出非法或命令失败时不误报成功，不停止或重启核心服务。
27. 主页面标题及设置页均不再出现独立核心文件版本字段，运行版本、来源与错误诊断仍可见；工具版本及更新比较、升级校验行为保持不变。

## 8. v2rayN 实现参考与适用范围

### 8.2 真延迟测试

1. `SpeedtestService.RunRealPingAsync` 调用 `CoreManager.LoadCoreConfigSpeedtest`，生成专用配置并启动临时核心进程。
2. Xray 配置生成器为被测节点分配本地回环监听端口，并建立对应的入站与出站路由。客户端通过相应的 SOCKS5 端口访问配置的测试 URL，计量请求时间，最后停止临时进程。
3. 该方法说明“没有直接测速 API”并不等于“桌面客户端无法实现测速”。但它需要完整节点配置、可执行核心、独立端口和临时进程管理，属于客户端组织的测试流程。
4. 如后续采用此方案，节点仍优先通过 API 获取，但需验证返回数据是否足以重建配置，包括 DNS、链式出站、资源文件和其他依赖；无法重建的节点显示不支持，不能假定复制单个 outbound 就一定等价。
5. 扩展方案应使用 HTTPS 测试 URL，限定并发和超时，校验 TLS 证书，并明确测量范围及多次请求的取值规则；不需要加入取消按钮。测试不得修改生产服务的选择，退出时清理临时进程和配置。

### 8.3 分组接口与 Xray 接口的区别

1. v2rayN 的 `ClashApiManager` 使用 HTTP `/proxies`、`/proxies/{name}/delay` 和对分组的 PUT 请求，完成分组读取、延迟测试和节点切换。
2. 已核对的 `ClashProxiesViewModel` 自动刷新条件包含运行 sing-box，手动切换要求返回类型为 `Selector`。这条调用链不能证明 Xray 原生 gRPC API 提供相同功能。
3. v2rayN 的 Xray 分组生成代码会构造 balancer 策略与观测配置，属于客户端持有分组数据后生成核心配置，不是从 Xray API 自动发现全部分组。
4. XrayDeck 保留 Xray gRPC 作为核心控制接口，不将上述 Clash HTTP 路径作为 Xray 能力探测依据，也不为复用这些接口而更换核心。按最终范围，分组 API 不支持即放弃，不转为生成核心配置的方案。

源码：[ClashApiManager](https://github.com/2dust/v2rayN/blob/95f438abc93714150adf55acac7ceb03b3713032/v2rayN/ServiceLib/Manager/ClashApiManager.cs)、[ClashProxiesViewModel](https://github.com/2dust/v2rayN/blob/95f438abc93714150adf55acac7ceb03b3713032/v2rayN/ServiceLib/ViewModels/ClashProxiesViewModel.cs)、[V2rayBalancerService](https://github.com/2dust/v2rayN/blob/95f438abc93714150adf55acac7ceb03b3713032/v2rayN/ServiceLib/Services/CoreConfig/V2ray/V2rayBalancerService.cs)。官方定义：[Xray 路由与均衡策略](https://xtls.github.io/config/routing.html)。

### 8.4 版本、更新与统计

1. v2rayN 的 `UpdateService.GetCoreVersion` 执行本地核心的版本参数并解析输出；`CoreInfoManager` 定义 Xray 的发布源、版本参数及各架构下载包。可参考其版本识别、渠道区分和下载组织方式。
2. XrayDeck 管理的是 WinSW 托管的既有服务，升级仍需按照第 3.7 节处理实例关联、UAC、停服和失败回滚，不能直接套用应用自管核心的替换流程。
3. 已核对的 `StatisticsXrayService` 通过 Metrics 的 `/debug/vars` 读取流量统计。该 HTTP 端点与 gRPC API 地址不同，需核心另行开启 Metrics，不能从 API 端口推断其可用，也不能将流量统计当成节点延迟。
4. 官方连接观测文档说明 Observatory 与 Burst Observatory 的配置和调度；“突发连接观测”不是面向客户端的按需测速 RPC。
